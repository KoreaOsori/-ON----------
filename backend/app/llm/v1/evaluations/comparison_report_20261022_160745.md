# Sonnet thinking 설정 및 성분 설명 변경 후 검증

2026-10-22 로컬 Python에서 http://ec2-54-197-92-156.compute-1.amazonaws.com/api/llm/v1/ask 로 동일한 5개 질문을 Haiku/Sonnet 각각 1회 전송했다. 총 10회이며 클라이언트 재시도나 EC2 명령 실행은 없었다. 원본은 `comparison_20261022_160745.json`이다.

## 확인 결과

- HTTP 200은 10/10이다. Sonnet의 이전 503 오류는 이번 5회 모두 재현되지 않았다.
- 응답은 모두 status/answer/usage의 세 필드이며 usage에는 routing만 있다.
- Haiku 평균 3.731초(2.769~5.603초), Sonnet 평균 6.020초(2.576~15.086초). 각 5회뿐이므로 일반적인 모델 성능 우열로 해석하지 않는다.
- 두 모델 모두 용각산 조회 성분 5개 중 비교 연결 0개, 원비디 7개 중 1개로 설명했다. 이전의 '두 제품 모두 일부 연결'과 '용각산 연결 없음' 사이 모순은 이번 응답에서 해소됐다. 제품쌍 금기 미발견과 안전 보장을 구분하고 성분 비교 미진행도 안내했다. 이 수치는 응답 간 일관성을 확인한 것이며 실제 Gold 원문을 독립 대조한 것은 아니다.
- 다만 Haiku의 해당 병용 답변은 제형·복합제 조건에 대한 한계를 별도로 명시하지 않았다. Sonnet은 이를 명시했지만 '결과를 그대로 믿기에는 한계'라는 표현이 조회 사실과 적용 한계를 명료하게 구분하지 못한다.
- Sonnet 주의사항 응답은 status=insufficient_data, answer='답변을 끝까지 작성하지 못했어요. 질문 범위를 조금 줄여 다시 요청해 주세요.'였다. HTTP 성공과 사용자 질문 해결 성공을 구분해야 한다. stopReason 및 재작성 횟수가 응답에 없어 출력 한도 원인이나 재시도 실행 여부는 확정할 수 없다. 코드상 max_tokens 또는 다른 미완료 종료/빈 답변 경로를 조사해야 한다.
- Haiku 제외 제품 재언급은 이전 실행에서 없었으나 이번에 재발했다. '등록된 제품으로 확인되지 않아'라고 표현하고 불필요한 제품명·제조사 확인을 요청했다. 프롬프트 규칙만으로 제외 제품 처리의 일관성이 보장되지 않는다.

## 범위와 후속 과제

이번 검증은 배포 API의 응답 동작과 표현 일관성 점검이다. DB·벡터 실제 조회 로그, 실제 Bedrock 모델 ID, 의료 원문 전체, 금기 양성 사례, 확정된 건강기능식품과의 병용은 검증하지 않았다. routing 사용량만으로 전체 추론 비용을 비교할 수 없다.

후속 우선순위는 Sonnet 미완료 종료 원인/출력 예산 확인, 제외 제품이 답변 생성 맥락에서 다시 문의 대상으로 취급되지 않도록 구조화, 제형·복합제 적용 한계의 간결한 보존이다. 이번 작업에서는 서비스 코드를 변경하지 않았다.
