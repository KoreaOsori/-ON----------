# 약ON 벡터 DB 파이프라인 개발 보고서

2026년 10월 24일 · 구현 기준: `vector_pipeline` v2.1 및 후속 AWS 연결·동기화 기능

## 요약

**의약품과 건강기능식품 Silver 데이터를 하나의 PostgreSQL 벡터 저장 구조로 통합하는 파이프라인을 구현했다.** S3에서 최신 공통 날짜의 데이터를 선택하고, 검색용 문서 생성·중복 제거·임베딩·RDS 적재·공개 전환까지 하나의 명령으로 실행할 수 있다.

초기 구조의 문제였던 DUR JSON 분할, 제품별 중복 임베딩, 장애 시 재호출, 검색 경로 부재를 보완했다. 동일한 본문은 한 번만 임베딩하고 제품과 출처는 별도 연결 정보로 보존한다.

- **데이터:** 의약품 39,802개와 건강기능식품 45,938개, 총 85,740개 제품의 로컬 변환을 검증했다.
- **중복 감소:** 고유 임베딩 입력을 1,148,323개에서 334,928개로 약 70.8% 줄였다.
- **복구:** 성공 임베딩을 영구 캐시에 저장하고, 실패 문서 격리·재시도와 DB 적재 체크포인트를 구현했다.
- **검색:** 제품명을 먼저 식별한 후 연결된 문서를 검색하고, 같은 본문의 중복 결과가 top-k를 채우지 않도록 구성했다.
- **운영:** EC2 Docker, S3, Secrets Manager, RDS 연결 설정과 수동 동기화·롤백·정리 명령을 준비했다.
- **검증:** 2026년 10월 24일 로컬 테스트 46개와 Docker Compose 설정 검사를 통과했다.

**현재 상태는 코드 구현 및 로컬 검증 완료다. 실제 EC2 배포, Bedrock 전체 임베딩, RDS 적재 성공, 검색 품질·처리 시간·비용은 이 작업에서 확인하지 않았다.** 아래 대량 데이터 수치는 2026년 10월 13일 스냅샷의 기존 로컬 변환 결과이며, 현재 S3 최신 데이터의 실측 결과가 아니다.

## 목표와 제약

**목표는 원본 정형 데이터와 검색용 벡터를 분리하면서, 의약품·건강기능식품 정보를 같은 검색 경로에서 사용할 수 있게 하는 것이다.**

| 구분 | 원칙 | 설계에 미친 영향 |
| --- | --- | --- |
| 작업 범위 | `vector_pipeline`만 변경 | 수집·Gold·백엔드·Terraform 코드는 수정하지 않음 |
| 데이터 역할 | 원본 정보는 별도 Gold 영역에서 관리 | 벡터 영역에는 검색 본문과 제품·원본 연결 정보 저장 |
| 저장소 | PostgreSQL RDS 사용 | pgvector 확장과 `product_search` 스키마 구성 |
| 실행 환경 | EC2 Docker에서 실행 | 컨테이너 작업과 RDS 저장소 분리 |
| 비용 | 같은 본문을 반복 임베딩하지 않음 | 본문 해시 기반 중복 제거와 영구 캐시 |
| 무결성 | 일부 누락된 결과를 정상 데이터로 공개하지 않음 | 전체 검증 완료 후 활성 스냅샷 전환 |
| 최신성 | 두 제품군의 날짜를 맞춤 | 최신 공통 날짜 선택, Parquet 내부 날짜 대조 |
| 인증 | `.env`에 DB 비밀번호를 넣지 않음 | TOML 설정 + EC2 IAM 역할 + Secrets Manager |
| 복구 | 실패 후 성공 작업을 재사용 | 캐시, 실패 목록, 배치 체크포인트, 롤백 |

벡터 검색은 관련 근거를 찾는 기능이다. 검색 결과 자체가 의료적 판단이나 병용 안전성 판정의 정확도를 보장하는 것은 아니며, 해당 판단 기능의 검증은 이 보고서 범위에 포함하지 않는다.

## 전체 파이프라인 구조

**실버 파일은 문서 생성·검증·임베딩·적재를 거쳐, 검증된 실행 결과만 검색에 공개된다.**

```text
S3: silver/drug_product/ + silver/health_food_product/
  ↓ 두 제품의 data.parquet이 모두 있는 최신 공통 날짜 선택
  ↓ ETag 조건부 다운로드 및 Parquet snapshot 확인
검색용 문장 생성
  ├─ 제품 개요·성분·효능·용법·주의사항 등
  └─ DUR 규칙 → 사람이 읽는 조건·주의 문장
  ↓ 청크 병합·분할, 공통 본문 중복 제거
로컬 bundle
  ├─ documents.jsonl: 고유 임베딩 입력
  ├─ links.jsonl: 제품·본문·출처 연결
  ├─ rejects.jsonl: 격리된 규칙
  └─ manifest.json: 개수·해시·완전성 정보
  ↓ 무결성 검증
Bedrock Titan V2 ↔ SQLite 영구 캐시·실패 목록
  ↓ 캐시의 벡터를 배치 적재
RDS PostgreSQL / product_search
  ├─ 고유 벡터
  ├─ 실행별 제품 연결
  └─ 적재 진행 상태
  ↓ 전체 적재 완료 후 active_snapshot 전환
제품명 식별 → 제품 범위 필터 → 정확 코사인 검색 → 제품·출처 반환
```

Gold 원본 저장은 별도 작업이다. 여기서 구현한 것은 Silver를 입력으로 사용하는 검색용 데이터 가공·적재 경로이며, Gold 적재까지 구현했다고 보지 않는다.

## 개발 과정

**초기 대량 변환 구조에서 출발해, 중복 제거와 장애 복구를 먼저 개선하고 검색·운영 기능을 추가했다.** 다음 표는 작업 순서를 정리한 것이며 모든 단계의 개별 완료 날짜를 의미하지 않는다.

| 단계 | 확인된 문제·요구 | 구현 및 결정 |
| --- | --- | --- |
| 1. 입력 분석 | 두 제품군의 Parquet을 통합 검색에 사용 | 공통 문서 형식과 제품 유형 구분 도입 |
| 2. 초기 청크 생성 | 조항마다 작은 청크가 많음 | 짧은 인접 조항 병합, 최대 길이·중첩 분할 적용 |
| 3. DUR 개선 | JSON 내부 코드가 본문을 차지하고 JSON 중간이 잘림 | 의미 있는 필드만 문장화, 규칙 조건 반복·출처 보존 |
| 4. 중복 제거 | 모든 청크의 제품명 때문에 제품 간 캐시 공유 불가 | 제품명·업체명 접두어를 개요 중심으로 제한, 본문과 제품 연결 분리 |
| 5. 임베딩 복구 | 중간 실패 시 이미 호출한 결과 손실 | SQLite 즉시 저장, 제한된 병렬 처리 |
| 6. 실패 격리 | 특정 입력 오류가 전체 실행을 막음 | 실패 기록·건너뛰기·명시적 재시도, 시스템 오류 별도 처리 |
| 7. 적재 개선 | 전체 TEMP 적재와 마지막 단일 커밋 | 배치 COPY와 진행 위치의 동시 커밋 |
| 8. 검색 구현 | 제품명이 없는 일반 청크의 검색 연결 부족 | 제품명 후보 조회 → 해당 제품의 연결 청크 검색 |
| 9. 운영 기능 | 이전 스냅샷 복구·정리 명령 부재 | 감사 이력 포함 rollback, 기본 dry-run prune |
| 10. 환경 연결 | 기존 EC2 역할·RDS·S3 구성과 불일치 | 현재 IAM 권한에 맞춘 S3 읽기, Secrets Manager 인증 |
| 11. 설정 정리 | `.env` 없이 DB 연결 요청 | `settings.toml`과 읽기 전용 `check-db` 추가 |
| 12. 최신 동기화 | 날짜별 S3 데이터를 자동 선택할 필요 | 최신 공통 날짜 탐색, `sync-silver` 통합 명령 추가 |

## 단계별 구성 요소

### 1. S3 입력과 날짜 선택

기본 버킷은 `pill-check-data-827913617635`, prefix는 `silver`다. 아래 두 형식의 날짜 폴더를 지원한다.

```text
silver/drug_product/snapshot=YYYY-MM-DD/data.parquet
silver/health_food_product/snapshot=YYYY-MM-DD/data.parquet

또는 각 제품 폴더 아래 YYYY-MM-DD/data.parquet
```

- S3 목록의 전체 페이지를 조회하고 폴더명의 날짜로 비교한다.
- 두 제품군에 모두 존재하는 가장 최근 날짜를 선택한다.
- 한쪽만 더 최신이면 이전 공통 날짜를 사용하며, 공통 날짜가 없으면 중단한다.
- 0바이트 파일, 임시 파일, 잘못된 날짜는 제외한다.
- 같은 제품군·날짜에 두 경로가 있으면 모호한 입력으로 보고 중단한다.
- 다운로드는 현재 객체에 ETag 조건을 붙여 수행하고 응답의 VersionId를 기록한다. 두 파일 전체를 하나의 S3 트랜잭션으로 고정하는 것은 아니다.
- Parquet 각 행의 snapshot이 선택한 날짜와 같은지 확인한다.

초기에는 `_latest.json` 완료 포인터를 사용하는 경로를 구현했지만, 현재는 사용자의 날짜 폴더 요구에 맞춰 파일 목록 기준으로 변경했다. **파일 존재만으로 원본 수집 전체 완료를 증명할 수는 없으므로 두 제품 업로드가 끝난 뒤 실행해야 한다.**

### 2. 문장화·청크 생성

| 항목 | 현재 기준 |
| --- | --- |
| 정보 유형 | 개요, 성분, 효능, 용법, 주의사항, 보관 등 |
| 청크 최대 길이 | 1,800자 |
| 짧은 조항 병합 목표 | 900자, 모든 청크의 최소 길이를 보장하는 값은 아님 |
| 긴 본문 분할 중첩 | 150자 |
| 제품명·업체명 | 개요 청크와 메타데이터에 보존 |
| 동일 본문 | 본문 해시로 공유, 제품 연결은 별도 보존 |
| 출처 | 원본 참조, 제품 키, snapshot, 규칙 메타데이터 유지 |

**1,800은 토큰 수가 아니라 문자 수다.** 같은 길이여도 실제 모델 입력 토큰 수는 본문 구성에 따라 달라진다. 원문 본문 자체에 들어 있는 제품명까지 임의로 삭제하지는 않는다.

DUR는 JSON 전체를 임베딩하지 않는다. 성분·제형·연령·등급·최대용량·기간·금기 내용·비고 등 읽을 수 있는 정보를 문장으로 구성하고 내부 연결 코드는 메타데이터로 분리한다. 서로 다른 규칙은 무리하게 합치지 않으며 긴 본문을 나눌 때 조건을 각 조각에 반복한다.

조건이 너무 길어 정상 청크를 만들 수 없으면 해당 규칙을 `rejects.jsonl`에 기록하고 다른 규칙·제품 처리는 계속한다. 단, 격리된 규칙이 있으면 bundle을 불완전 상태로 표시해 공개하지 않는다. 남은 예산 301자·중첩 150자의 경계 오류도 별도 DUR 조건 오류로 처리하도록 수정했다.

### 3. 임베딩과 캐시

| 항목 | 구현 |
| --- | --- |
| 제공자 | AWS Bedrock |
| 모델 | `amazon.titan-embed-text-v2:0` |
| 기본 차원 | 1,024, 코드상 256·512도 지원하나 DB 설정 일치 필요 |
| 정규화 | 활성화 |
| 호출 단위 | 고유 문서 청크 1개당 요청 1회 |
| 동시 호출 | 기본 4개, workers 옵션으로 제한 |
| 내부 처리 배치 | 기본 128개, 한 요청에 128문서를 보내는 의미는 아님 |
| 캐시 | 본문 해시 + 모델·차원·정규화 버전별 SQLite 저장 |
| 질문 검색 | 질문도 같은 모델로 임베딩 |

성공 응답은 DB 적재와 별개로 캐시에 즉시 저장한다. 문서 입력 오류는 실패 테이블과 JSONL에 기록하고, 재실행 시 기존 실패를 건너뛰며 다른 문서를 처리한다. 원인을 수정한 후 `--retry-failed`로 재시도할 수 있다.

권한·자격증명·연결·서비스 장애는 문서 결함으로 기록하지 않고 실행 오류로 처리한다. 임베딩 실패가 남아 있으면 공개하지 않으며 종료 코드 2를 반환한다. 캐시가 사라진 경우 RDS에 존재하는 벡터를 자동으로 캐시에 복원하는 기능은 없다.

### 4. RDS 저장·공개

**고유 본문 벡터와 제품 연결을 분리해, 동일 본문을 여러 제품이 참조한다.** 두 제품군은 같은 벡터 테이블에 저장하고 `product_type`으로 구분한다.

| 객체 | 역할 |
| --- | --- |
| `pipeline_config` | 스키마 버전과 임베딩 모델·차원 검증 |
| `product_vectors` | 고유 본문과 벡터 |
| `product_links` | 실행별 제품·본문·출처·조건 연결 |
| `ingestion_runs` | 실행 식별자, manifest, 진행 위치, 완료 상태 |
| `active_snapshot` | 현재 검색에 공개한 실행 결과 |
| `active_product_links`, `active_vectors` | 활성 결과 조회용 뷰 |
| `publication_events` | 공개·롤백의 전후 실행 및 사유 이력 |

DB 이름은 `pill`, 실제 파이프라인 스키마는 `product_search`다. 인프라 주석의 `rag`와는 이름이 다르며 자동 이름 변경은 하지 않았다. Gold·백엔드 테이블을 변경하지 않는다.

배치 COPY 적재와 체크포인트 갱신을 같은 트랜잭션으로 커밋한다. 실패하면 같은 bundle로 중단 위치부터 재개할 수 있다. 전체 완료 후 공개 포인터를 전환하므로 적재 중간 결과를 검색에 노출하지 않는다. 새 스냅샷에서 삭제된 제품은 활성 검색에서 제외되지만 이전 실행과 벡터를 즉시 물리 삭제하지 않는다.

HNSW 인덱스 생성은 초기 테이블 생성과 분리했다. `create-index`로 적재 후 생성할 수 있으나 `sync-silver`가 자동으로 생성하지는 않는다.

### 5. 제품명 검색과 벡터 검색

제품명 질문은 호출자가 제품명 또는 제품 키를 명시하는 구조다. 자유문장에서 제품명을 자동 추출하는 기능은 구현하지 않았다.

1. 활성 실행의 개요 청크에서 제품명을 정확 일치·접두어·3자 이상 포함 검색 순으로 조회한다.
2. 제품 후보가 없으면 전체 검색으로 확대하지 않고 빈 결과를 반환한다. 후보가 20개를 넘으면 범위를 구체화하도록 오류를 반환한다.
3. 활성 실행·제품·유형 등 필터를 적용한 후보를 먼저 확정한다.
4. 정확 코사인 거리로 고유 본문의 top-k를 선택한다.
5. 본문당 최대 50개 제품 출처와 전체 출처 수를 연결해 반환한다.

이름 조회에는 개요 행 전용 B-tree와 pg_trgm GIN 인덱스를 준비했다. 벡터 검색은 HNSW 근사 후보를 필터링하는 방식 대신 정확 검색을 사용한다. 이는 근사 검색 때문에 후보가 누락되는 문제를 피하지만, 의미상 관련 문서의 재현율이나 의료적 정확도를 검증했다는 뜻은 아니다. 전체 범위 검색 비용과 지연시간은 별도 측정이 필요하다.

### 6. 롤백·정리·동기화

| 기능 | 동작 |
| --- | --- |
| 일반 공개 | 과거 날짜로 자동 전환하는 동작 차단 |
| `rollback` | 보존된 완료 실행으로 명시적 전환, 사유·전후 실행 기록 |
| `prune` | 기본은 삭제 계획만 출력, `--apply`일 때 삭제 |
| 보존 정책 | 활성 실행·최근 완료 실행 보존, 미완료 실행 기본 보존 |
| 중단된 정리 | pruning 상태로 표시하고 다음 정리에서 재개 |
| 고아 벡터 | 보존된 연결이 없는 벡터 정리, loading 실행이 있으면 보류 |
| `sync-silver` | 최신 날짜 선택 → prepare → validate → embed → ingest → 공개 |

동기화는 호출 한 번당 한 번 수행한다. 상시 감시·cron·자동 스케줄러는 등록하지 않았다. 같은 날짜의 파일을 수정한 경우 다음 동기화에서 다시 읽고 새 bundle을 생성하며, 변경되지 않은 본문의 임베딩은 캐시를 재사용한다.

## 최종 결과: 초기 v1과 개선 v2 비교

**같은 제품 데이터에 대해 고유 임베딩 입력과 제품 연결 수가 감소했다.** 아래 v1/v2 수치와 파일 크기는 기존 측정 기록이며, v2.1 전체 재변환에서도 고유 문서·연결 수는 동일했다.

| 지표 | 초기 v1 | 개선 v2 | 변화 |
| --- | ---: | ---: | --- |
| 제품별 청크·연결 수 | 1,148,978 | 877,696 | 약 23.6% 감소 |
| 고유 임베딩 입력 수 | 1,148,323 | 334,928 | 약 70.8% 감소 |
| JSONL 전체 크기 | 1,942,544,218바이트 | 961,118,831바이트 | 약 50.5% 감소 |

| v2.1 전체 변환 항목 | 결과 |
| --- | ---: |
| 제품 수 | 85,740 |
| 고유 문서 | 334,928 |
| 제품 연결 | 877,696 |
| DUR 격리 규칙 | 0 |
| 고유 입력 본문 총 길이 | 151,451,082자 |

고유 입력 수 감소는 캐시가 비어 있을 때 필요한 문서 임베딩 요청 수를 줄이는 근거다. **요금이 동일 비율로 감소했다고 측정한 것은 아니다.** 실제 과금은 모델의 토큰 산정과 재시도 등에 따라 달라지며 현재 코드는 입력 토큰 수를 기록하지 않는다.

334,928개 벡터 × 1,024차원 × float32 4바이트는 1,371,865,088바이트, 약 1.37GB다. 이는 벡터 값만의 계산값이며 본문·제품 연결·인덱스·행 오버헤드·WAL·이전 실행 보존 공간을 포함한 실제 RDS 용량이 아니다.

## EC2 운영 설정과 수동 실행

**일반 설정은 파일에서, 비밀번호는 연결할 때 Secrets Manager에서 읽는다.**

| 항목 | 설정·동작 |
| --- | --- |
| 설정 파일 | `settings.toml`, 컨테이너 읽기 전용 마운트 |
| 리전 | us-east-1 |
| DB | pill / product_search |
| RDS 호스트·시크릿 식별자 | 사용자가 제공한 값으로 settings.toml에 설정 |
| DB 인증정보 | Secrets Manager에서 연결마다 조회, 파일 저장 안 함 |
| AWS 인증 | EC2 IAM 역할 |
| TLS | verify-full, `/certs/global-bundle.pem` |
| 로컬 지속 데이터 | `output/` bind mount의 bundle·캐시 |
| 네트워크 | Linux EC2 host network override |

공유용 본문에는 비밀번호를 포함하지 않았다. 접속 호스트와 시크릿 식별자의 전체 값은 프로젝트 설정 파일을 기준으로 관리한다. DB 설정은 환경변수로 덮어쓰지 않으며, 임베딩 관련 환경변수 오버라이드는 기존 호환성을 위해 남아 있다.

RDS 실행 상태, EC2→RDS 5432 경로, Secret·S3·Bedrock 권한, CA 인증서와 output 쓰기 권한이 준비되어 있어야 한다. EC2의 `vector_pipeline/`에서 다음 순서로 실행한다.

```sh
# 이미지 준비
docker compose -f compose.yaml -f compose.ec2.yaml build

# 읽기 전용 연결 확인
docker compose -f compose.yaml -f compose.ec2.yaml run --rm pipeline check-db

# 최초 스키마 준비
docker compose -f compose.yaml -f compose.ec2.yaml run --rm pipeline init-db

# 업로드 완료 후 최신 데이터 동기화: 임베딩 비용 발생
docker compose -f compose.yaml -f compose.ec2.yaml run --rm pipeline sync-silver --workers 2

# 제품명 조회: 질문 임베딩 호출 없음
docker compose -f compose.yaml -f compose.ec2.yaml run --rm pipeline search --product-name 타이레놀 --product-type drug
```

HNSW가 필요한 운영 경로를 추가할 경우 대량 적재 후 `create-index`를 별도로 실행한다. 현재 정확 검색은 이 인덱스를 사용하지 않는다. 정리 정책은 `prune`으로 먼저 계획을 확인하고 적용하며, 삭제된 실행으로는 롤백할 수 없다.
